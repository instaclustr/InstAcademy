# Chapter 4 diagram recommendations

This report recommends eight diagrams for Chapter 4, each with an exact placement and a self-contained prompt you can paste into ChatGPT to generate the image.

## Diagram 1: The chunking ingest pipeline

**Placement:** Lesson 4-1, Step 4, after the opening paragraph ("This is the most sophisticated pipeline in the course...") and before the `PUT _ingest/pipeline/bookstore-chunking-pipeline` request block.

**Type:** Flowchart (left to right pipeline diagram).

**Why:** Students must hold three cooperating processors in their head at once, and the diagram shows what each one does to the document as it passes through.

**Creation prompt:** Create a left-to-right flowchart of an OpenSearch ingest pipeline with three processors. On the far left, draw a document card labeled "Incoming book document" with these fields listed inside: book_id, title, author, content (long text, about 2,000 words). Draw an arrow from this card into a large rounded container labeled "Ingest pipeline: bookstore-chunking-pipeline". Inside the container, place three boxes in a row connected by arrows. Box 1 is labeled "1. text_chunking" with these bullet lines under the title: "algorithm: fixed_token_length", "token_limit: 384 (about 75% of the 512-token model budget)", "overlap_rate: 0.2 (20% overlap between neighboring chunks)", "output: raw string array in content_chunks". Box 2 is labeled "2. script (Painless)" with the bullet line: "reshapes each raw chunk string into an object: { text, chunk_index }". Box 3 is labeled "3. text_embedding" with these bullet lines: "model: all-mpnet-base-v2", "embeds the full content field", "output: 768-dimension vector in content_embedding". Below Box 1, add a small inset illustration: a long horizontal bar representing the full text, split into three overlapping segments, with the two overlap regions shaded and a caption "20% overlap so a sentence on a chunk boundary survives in at least one chunk". On the far right, outside the container, draw an output document card labeled "Indexed document in bookstore-rag" showing: "content_chunks: [ {text, chunk_index: 0}, {text, chunk_index: 1}, ... ]" and "content_embedding: [768 floats]". Draw an arrow from Box 3 to this output card. Number the three processors visibly (1, 2, 3). Style: clean flat technical illustration for a video course slide, white background, limited color palette (blues and grays with one accent color), large readable labels, no logos, no watermark.

## Diagram 2: Anatomy of the bookstore-rag index

**Placement:** Lesson 4-1, Step 5, after the opening paragraph ("Now build the index this whole chapter revolves around...") and before the `PUT bookstore-rag` request block.

**Type:** Labeled illustration (annotated document structure).

**Why:** The mapping packs four deliberate design decisions (nested chunks, FAISS HNSW vector, exact-typed metadata, slow refresh) into one JSON blob, and a labeled picture lets students see each decision as a separate part of the document.

**Creation prompt:** Create a labeled illustration of one document inside an OpenSearch index. Title the illustration "bookstore-rag: one document, four deliberate design choices". Draw one large document card divided into four stacked sections, top to bottom. Section 1, labeled "Identity and content", lists: "book_id: keyword", "title: text", "author: text", "content: text (full book summary)". Section 2, labeled "content_chunks (type: nested)", shows three small child cards stacked with a slight offset inside the section, each child card containing "text: text" and "chunk_index: integer" with chunk_index values 0, 1, 2. Add a callout arrow to this section with the text "nested type keeps each chunk's text and index glued together as one queryable unit". Section 3, labeled "content_embedding (type: knn_vector)", shows a horizontal strip of small colored squares representing a vector, annotated with: "dimension: 768", "engine: FAISS", "method: HNSW", "space_type: l2", "m: 16 (graph connectivity)", "ef_construction: 128 (build care)". Section 4, labeled "Filterable metadata (exact types)", lists: "genre: keyword (not text)", "price: float", "rating: float", "publication_year: integer", "in_stock: boolean", with a callout arrow saying "exact types make filters cheap yes/no checks with no full-text analysis". Below the document card, add a footer bar labeled "Index settings" with three items side by side: "knn: true", "default_pipeline: bookstore-chunking-pipeline", "refresh_interval: 30s (a catalog updates nightly, so do not pay for 1-second freshness)". Style: clean flat technical illustration for a video course slide, white background, limited color palette (blues and grays with one accent color), large readable labels, no logos, no watermark.

## Diagram 3: Filtered k-NN versus post-filtering

**Placement:** Lesson 4-1, Step 8, after the opening paragraph ("Now the biggest single performance win in RAG retrieval...") and before the request block.

**Type:** Side-by-side comparison flowchart (two panels).

**Why:** The performance win only makes sense when students see that the filter runs before the vector pass instead of after it, and a two-panel comparison makes that ordering visible.

**Creation prompt:** Create a two-panel side-by-side comparison diagram of two vector search strategies. Both panels flow top to bottom. Left panel, titled "Post-filtering (wasteful)" with a subtle red or gray warning tint: step 1 is a box labeled "All 256 books in the catalog"; step 2 is a box labeled "HNSW vector scoring runs on the entire catalog" with a caption "compute spent on every book"; step 3 is a box labeled "Take top-k results"; step 4 is a box labeled "Then apply filters: genre = mystery, price <= $20, rating >= 4.0"; step 5 is a result box labeled "Few or zero survivors" with a caption "most of the scoring work is discarded". Right panel, titled "Filtered k-NN (efficient)" with the accent color: step 1 is a box labeled "All 256 books in the catalog"; step 2 is a box labeled "Filter first: genre = mystery, price <= $20, rating >= 4.0" with a caption "only 6 books qualify in the sample data"; step 3 is a box labeled "FAISS scores only the 6 qualifying books"; step 4 is a result box labeled "Top matches returned, every one satisfies the constraints". In the left panel, visually shade or gray out a large share of the flow to represent wasted work. Between the panels or at the bottom, add one callout line: "Hand the filter to the engine before the vector pass and FAISS never scores books that fail the constraints." Style: clean flat technical illustration for a video course slide, white background, limited color palette (blues and grays with one accent color), large readable labels, no logos, no watermark.

## Diagram 4: Hybrid search score normalization and blending

**Placement:** Lesson 4-1, Step 9, after the opening paragraph ("This should feel familiar from Chapter 3...") and before the `PUT _search/pipeline/bookstore-hybrid-pipeline` request block.

**Type:** Flowchart (two branches merging into one pipeline stage).

**Why:** Students struggle to see why raw BM25 and vector scores cannot be added directly, and the diagram shows the two incompatible scales entering the normalization processor and leaving as one blended 0 to 1 ranking.

**Creation prompt:** Create a flowchart showing how OpenSearch hybrid search blends two scoring systems. At the top, draw one box labeled "One hybrid query" that splits into two parallel branches. Left branch: a box labeled "BM25 keyword match" with the sub-lines "match on content: 'mystery novel with an unreliable narrator'" and "raw scores on an unbounded scale, example: 14.2, 11.7, 9.3". Right branch: a box labeled "k-NN vector search" with the sub-lines "content_embedding, 768-dim query vector, k: 10" and "similarity scores on a different scale, example: 0.71, 0.66, 0.58". Both branches flow down into a wide box labeled "normalization-processor (search pipeline: bookstore-hybrid-pipeline)". Inside that box show two stages: stage 1 labeled "normalization: min_max" with the caption "rescales each score list to the 0 to 1 range", and stage 2 labeled "combination: arithmetic_mean, weights [0.3, 0.7]" with the caption "weights map in clause order: 0.3 keyword, 0.7 vector, leaning semantic because shoppers describe what a book is about". Below the processor box, add a small worked example panel: "Example (illustrative): keyword normalized = 1.00, vector normalized = 0.62, final score = 0.3 x 1.00 + 0.7 x 0.62 = 0.73". At the bottom, draw one output box labeled "Single blended ranked list, scores in 0 to 1". Mark the raw score numbers as illustrative examples. Style: clean flat technical illustration for a video course slide, white background, limited color palette (blues and grays with one accent color), large readable labels, no logos, no watermark.

## Diagram 5: function_score reranking layers

**Placement:** Lesson 4-1, Step 10, after the reconciling note blockquote and before the request block.

**Type:** Stacked bar chart with a small flow header (additive score buildup for two example books).

**Why:** The query mixes a base relevance score with three additive business boosts, and a stacked bar comparison shows exactly how a slightly worse semantic match can still win the ranking.

**Creation prompt:** Create a diagram with two parts. Part 1, a small header flow across the top: a box labeled "k-NN retrieval finds the candidates (base relevance score)" with an arrow into a box labeled "function_score adds business signals (score_mode: sum, boost_mode: sum)" with an arrow into a box labeled "Final business-aware ranking". Part 2, the main area: a horizontal stacked bar chart comparing two example books. The x-axis is labeled "Final score" and runs from 0 to 4 with gridlines at 1, 2, and 3. Bar 1 is labeled "Book A: rating 4.6, published 2023, in stock" and is built from four stacked segments in distinct shades, each segment labeled with its name and value: "base k-NN score: 0.82", "rating x 0.1: +0.46", "published 2020 or later: +1.2", "in stock: +1.15", with a total label at the bar end: "3.63". Bar 2 is labeled "Book B: rating 3.1, published 2010, out of stock" and is built from two stacked segments: "base k-NN score: 0.90", "rating x 0.1: +0.31", with a total label at the bar end: "1.21", and two grayed-out placeholder segments after it annotated "+0 (published before 2020)" and "+0 (out of stock)". Add a legend mapping the four segment colors to: base k-NN score, field_value_factor on rating (factor 0.1, missing default 3.0), recency boost (publication_year >= 2020, weight 1.2), stock boost (in_stock = true, weight 1.15). Add one callout line under the chart: "Book B is the closer semantic match, but Book A wins the ranking because the business signals add up. Base scores are illustrative." Style: clean flat technical illustration for a video course slide, white background, limited color palette (blues and grays with one accent color), large readable labels, no logos, no watermark.
